# OpenLess HarmonyOS Host

[English](README.md) | [简体中文](README.zh.md)

ArkTS / ArkWeb Stage project that packages the React frontend offline into a HAP.
`openless-core` is integrated through ArkWeb JavaScript Proxy → ArkTS → Node-API → Rust C ABI.
Startup snapshot, capability query, settings read and field transaction writes, history and activity statistics, dictionary add/update/delete and enabled state, correction rule reads, style list, and startup video flag are wired up.
Data uses real file storage in the app sandbox, and HarmonyOS IPC never falls back to browser mock data. Unimplemented commands report an explicit error.
System microphone enumeration, authorization query, and PCM volume monitoring are wired up; the provider catalog, channel management, model list, and connection test are supported. Credentials are stored encrypted through the HarmonyOS Asset Store and restored at startup into the Rust in-memory adapter; channel metadata is persisted separately.
Network status keeps the desktop's real HTTP probe; external links go to the system browser, and the WebView intercepts navigation to external sites. Debug logs are exported through the system file picker.
The input method's AudioCapturer → PCM native bridge → core ASR/polishing pipeline → result preview → InputClient confirmed write is wired up. Real online recognition still requires a usable channel to be configured, after which it must be accepted on device.

## Current Completion Boundary

Style marketplace ZIP download, channel test result recording, dictionary suggestion accept/reject, and the ordinary cloud backup status/upload/restore/delete interfaces are wired up. History WAV reading, re-recognition, re-polishing, history delete and clear, correction rule add/delete/enable/disable, manual word collection, dictionary preset read/write, and system clipboard copy are complete. An isolated-sandbox self-check verifies word deduplication, rule enable/disable and deletion, preset read/write, and persistence after reopening storage; the test does not modify user data. There is also an offline voice check that uses isolated fixture ASR/polishing to verify PCM, result preview, no automatic insertion, cancellation and rejection of stale audio, WAV reading, re-recognition not overwriting a completed history entry, and re-polishing; it is not equivalent to real online recognition.

Mobile work that is still incomplete:

- Device acceptance of input method recording and real online ASR/polishing; word-by-word live transcription display and per-channel recording tests.
- End-to-end encrypted cloud sync's secure credential transactions, status events, and UI adaptation; ordinary cloud backup is connected to the shared service, but remote operations still need account configuration acceptance.
- HarmonyOS update detection and installation flow; the Android APK update cannot be invoked directly.

Desktop floating window, global hotkeys, Windows IME, Wayland, desktop CLI / Less Computer and similar commands are not completion criteria for the current phone and tablet build. `ipc-audit.json` is the shared static IPC coverage inventory and includes these desktop interfaces; a coverage percentage is neither the mobile completion percentage nor proof that an end-to-end feature works.

Cross-app input suggestions are primarily handled through IME Kit: the input method inserts text into the bound, focused editor through the system-assigned InputClient. Base permissions remain INTERNET and MICROPHONE; the input method must additionally declare the extension and be enabled by the user in system settings. The keyboard panel uses the input method framework, so an ordinary floating window does not need to be requested in order to show the panel.

This project uses the input method only and does not integrate an accessibility extension. A floating window itself provides no cross-app write capability; when the input method is not enabled, copying and then pasting manually is the fallback.

## Input Method Panel

`OpenLessInputMethod` is a system input method extension, and `pages/InputMethodPanel` is the native ArkUI keyboard panel, which does not go through the main settings page's WebView. librime 1.17.0, shared with Android, is integrated through Node-API, supporting offline pinyin, candidates, paging, space confirmation, Chinese/English switching, digits and punctuation, code backspace, and deletion through the system input box. Fcitx5 was not introduced, and no accessibility is used.

Enable "OpenLess Input Method" in the system settings' input method management, then switch to it in an ordinary input box. Only the input method extension and the existing network/microphone permissions are declared; no accessibility service is registered. The system-assigned InputClient is unbound on inputStop; queued keystrokes are not sent to an already unbound client; logs do not record input content.

The voice button records 16 kHz / mono / 16-bit PCM. When recognition finishes, the text is written directly into the currently bound input box; if the write fails, the result is kept for retry. Cancelling, collapsing, or unbinding releases the microphone and rejects late results; password input boxes disable voice. The extension reuses Asset Store credentials and reads the saved channel settings before a new session. The main app overview page provides an in-app recording entry that reuses VoiceClient and the same audio/ASR/polishing backend as the input method. Start, stop, cancel, volume events, and result preview are wired up; results can be copied and refresh history; leaving the page or entering the background cancels recording and rejects late results, and the microphone volume test is mutually exclusive with recording. Real online recognition still requires a usable channel to be configured and then accepted on device; simulated regression is not treated as online acceptance. In both the standard and split layouts, the space key supports 450ms long-press voice; short press and long press are mutually exclusive, and a long press does not enter an additional space. While held, the space key is retained to receive the release event; on release, recording stops, recognition runs, and the text is written directly. An operation released during the preparation phase is also retained; gesture cancellation, unbinding, and stale results are not written. Toolbar voice is still stopped with the end button, and successful results are likewise written directly.

References: [IME Kit](https://developer.huawei.com/consumer/cn/doc/harmonyos-guides-v5/ime-kit-V5), [input method insertion and pre-edit example](https://developer.huawei.com/consumer/cn/doc/doccenter-dev-faq/faqs-ime-7), [official extension ability template (includes Accessibility and InputMethod)](https://developer.huawei.com/consumer/cn/doc/doccenter-deveco-studio/ide-hmos-add-new-ability).

The input method extension has its own isolated sandbox; identical `filesDir` strings in the main app and the input method do not mean a shared configuration file. After main app startup and after configuration writes, the whitelisted voice settings and channel metadata are published to the app-exclusive Asset Store; before keyboard recording they are imported into its own backend, and the existing secure credentials are then restored. Snapshot shards respect the Asset Store's 1024-byte per-entry limit and become visible to readers only after the manifest is committed; an update during a read is retried, and mixed versions are not accepted. Snapshots contain no API Key, user dictionary, history, or cloud sync configuration. An unchanged snapshot does not overwrite the polishing mode selected separately on the keyboard. First use requires opening the main app first to publish the configuration. `harmony-voice-configuration.test.mjs` covers sharding, concurrent updates, and the size limit; a native test uses two independent data directories to verify that after the main app's multimodal settings are imported, a keyboard voice session can be started; it does not replace real online recognition acceptance.

Build from the repository root:

```bash
bash openless-all/app/scripts/build-harmony-frontend.sh
```

Requirements: frontend npm dependencies installed, HarmonyOS Command Line Tools, Python 3.
The toolchain defaults to `~/.local/share/harmony/current` and can be set through `OPENLESS_HARMONY_TOOLCHAIN`.
The first Rust build requires `rustup target add aarch64-unknown-linux-ohos`.
The cache defaults to `/data-win/openless-cache` and can be set through `OPENLESS_CACHE_ROOT`.

- `harmony/web-dist`: offline React assets, using relative URLs.
- `harmony/openless-project`: build project copy, project cache, and the HAP.
- `harmony/rust-target`: Rust HarmonyOS cross-compilation artifacts.
- `harmony/ohpm`: ohpm download cache.
- `cargo`: Rust dependency download cache.
- `harmony/hvigor`: Hvigor user cache and tool dependencies.
- `npm`: npm download cache used by this script.

The HAP is located at `harmony/openless-project/entry/build/default/outputs/default/`.
The repository maintains only the HarmonyOS source files; build intermediates are not written back into the HarmonyOS source project.
The frontend is built with `VITE_OPENLESS_PLATFORM=harmony` and uses the mobile capability configuration.

Package name `openless.hm.com`, compatible API 12, target API 20, compile SDK uses the machine's default version.
An unsigned HAP is generated first; if the certificate and Profile in the local signing directory are complete, the official tools generate `entry-default-signed.hap`.
The signing directory defaults to `~/.local/share/harmony/signing/local-test` and can be overridden with `OPENLESS_HARMONY_SIGNING_DIR`; the password is read from a local file and is not written into source configuration. Installing on a real device requires a Huawei debug certificate for that package name and a debug Profile that includes the target device.
A Profile for another package name cannot be used directly. Signing material must not be committed to the repository.
A successful compile does not mean a real-device run has been verified.

A normal build does not automatically run system probes and dictionary/voice/style-package self-checks when the WebView starts, avoiding contention with the first screen and with user operations for the backend. To diagnose a problem, set `OPENLESS_HARMONY_STARTUP_PROBES=1` explicitly; only diagnostic builds inject the original startup probe script.

The HarmonyOS build uses a single-file IIFE and a deferred ordinary script, and removes the crossorigin attribute from resource tags, avoiding module load failures caused by the rawfile's opaque origin; desktop and Android builds are unaffected.

Pages are loaded with `$rawfile('web/index.html')`, with JavaScript and DOM Storage enabled.
Reference: [Huawei web page loading documentation](https://developer.huawei.com/consumer/cn/doc/harmonyos-guides/web-page-loading).

Device runtime data is at the app's `filesDir/openless`, and runtime cache at `cacheDir/openless`; the unified directory on the computer is used for development build cache.
The WebView passes request tickets through synchronous request/takeResult, ArkTS executes system operations asynchronously, and Rust commands run in the background through Node-API async work. Avoid returning a Promise directly from the JavaScript Proxy, which different WebView versions parse incorrectly.
Microphone volume is returned through the local WebView's custom event, and the capturer is released after the list is closed. On API 24, input device switching follows system routing, and a microphone that is not on the current route cannot be forced.

The panel follows the Xiaoyi input method layout: light grey background, white rounded keycaps, a compact toolbar, and no permanent brand text. The toolbar's layout button switches between standard, split, and floating keyboards, and the choice is saved locally; the standard and split modes have a separate number row, and when landscape space is insufficient the number row is hidden and key heights are compressed. Split mode includes a blank centre, spaces on both sides, duplicated G/V keys, and bottom entries for input method switching, punctuation, emoji, and digits.

Floating mode uses the IME Kit native `FLG_FLOATING` panel, with a draggable top bar, − / + for resizing, and ↙ to restore the fixed keyboard; position and size are saved locally and constrained to the current screen. No ordinary floating window permission or accessibility is needed. The panel re-fits its size when the screen orientation changes and when it is shown again.

A compatible runtime may not support `getEditorAttribute`. When that interface errors or has not returned within 1.2 seconds, a Rime private session continues to provide Chinese candidates, the personal dictionary is not read or trained, voice is disabled, and Enter inserts a newline; a late attribute result cannot re-enable learning. A detected password box still offers English only. Text writing is still performed by the system-assigned `InputClient`, and whether a compatible environment supports writing must be verified on a real device. `scripts/harmony-editor-compat.test.mjs` covers attribute errors, timeouts, late results, password boxes, and stale clients.

All hosts use IME Kit's asynchronous write/delete interfaces, avoiding blocking the keyboard on the compatible bridge's synchronous IPC. Except for the compatible-bridge strategy described below, a write is sent only once: the commit is confirmed when the interface succeeds or the system `textChange` notification strictly matches the complete text after this selection replacement. The latter requires having previously received the current input box's text and selection notifications; a bare cursor move, a missing baseline, or non-matching text cannot prove success. Text kept for matching is held in memory for at most 4096 UTF-16 units and is cleared when the input box changes; manual recovery clears only this confirmation target and keeps the current input box baseline for the next write match; password boxes and input boxes with unknown attributes do not retain text notifications. Logs do not record input content. The write/delete wait limit is 800 milliseconds; an unconfirmed word stays in Rime, and the toolbar offers "Written" (ack only, no re-insertion), "Retry write", and "Cancel pending commit". Whether Zhuoyitong provides enough notifications to complete automatic confirmation still requires device acceptance.

Device feedback confirms that Zhuoyitong's text notifications and read-back are both unavailable. For non-password edit boxes whose attributes are readable and whose package name is empty or `com.droi.tong`, commit, delete, and editor actions such as search/done use a single asynchronous send, and Rime then releases the text already handed to the system and continues composing; a missing host receipt is not a precondition for the next input, and no first-time manual confirmation is required. No automatic resend is performed. Here the Rime ack means the text has been handed to the system interface, not that the host confirmed insertion; when false or an unexpected error is explicitly returned, the user is prompted to check the input box, and the bridge's `12800003`, which is also returned for operations that did actually insert text, is only logged for diagnostics, avoiding a late receipt locking the keyboard again. Results for an old input box do not affect a new one. Unknown attributes and password boxes do not use this commit strategy. A compatible bridge with no confirmation receipt still cannot provide the same write-success guarantee as a normal native editor, and real continuous input and continuous deletion require device verification.

"Written" and "Cancel pending commit" do not wait for the pending client write queue, and recovery invalidates old tasks; an old confirmation/failure cannot overwrite the state after recovery or confirm a new word. "Retry" is disabled while waiting for confirmation; a timeout also does not resend automatically, and the user should check the input box and choose "Written" once text has appeared. Switching input boxes establishes a new queue and releases the old Rime session, so an unresponsive request from an old client does not hold up initialization of the new input box. Regression checks include exact text notifications, error notifications, no baseline, a write that never returns, continuing to type after manual confirmation, late results, password boxes, and input box rebinding.

Candidate bar content is left-aligned; 60ms after typing stops it prefetches to at least 32 candidates (showing all when there are fewer), and scrolling right to the end appends about 32 more native candidates each time, keeping already loaded candidates and the native order; appending is read-only through the native candidate iterator and does not change the menu page, the input version, or the top candidate, and after appending, candidates are selected by native absolute index, with new pinyin resetting the scroll position. Load requests are serialized, deduplicated, and checked against the input version, and cloud candidates do not change native indices. Once expanded, 2–6 candidate columns are shown according to available width, scrolling up and down to the end continues to append, and duplicate requests and candidate index changes are prevented during loading. The numeric nine-grid and the symbol pages are independent, and comma, period, common symbols, and long-press punctuation follow Chinese/English switching. Letter and digit keys use a symbol hint in the top-right corner: a preview appears after a 350ms long press or a clear upward swipe, and release inserts only once, without entering the original letter; the swipe switch is read from live storage at recognition and commit time, and a move beyond 10vp cancels the long press, preventing a slow swipe from falling into the long-press path. Swipe distance is limited to 22–30vp with the key height, horizontal offset is also limited, and sliding back cancels. The top feedback area distinguishes "Entered", confirmed by a native editor, from "Sent", dispatched once by a compatible editor. `scripts/harmony-symbol-gesture.test.mjs` verifies gesture mutual exclusion, cancellation, editor switching, accidental-touch distance, and split keyboard mapping. Long-press delete, single-shot uppercase and caps lock, Chinese/English switching, and long-press switching to the system input method are supported. The emoji and tools pages are connected to real operations; voice keeps recording, ending, preview confirmation, and cancellation. Colours follow the system through ArkUI light/dark resources and do not change the main app's settings layout. `scripts/harmony-panel-layout.test.mjs` checks modes, persistence, resizing, drag boundaries, landscape, and fallback when native switching fails; real touch and display still depend on device verification.

Letter keys and the top number keys fill the panel's available width, keeping only a normal 6vp margin on each side. The standard, thumb (split), and one-handed layouts share compact row heights and panel height and do not change height when switched; on wide screens keys may become horizontal rectangles, avoiding the keyboard growing taller when filling the width; the standard layout uses 7vp horizontal and vertical spacing. Height is also limited by available screen space, ensuring every row is fully usable in landscape; function keys keep a wider size. Panel height follows the actual keyboard row height, avoiding a large blank area when the floating keyboard narrows. Keys have a 10vp corner radius, with a grey background and white keys plus a 2vp bottom shadow; the toolbar uses rounded SVG icons for light and dark respectively. All buttons provide a 90ms press scale/opacity transition that does not change write timing or long-press/swipe recognition. The two symbol pages, the bottom punctuation, and key badges follow the current Chinese/English mode, and the numeric decimal point remains half-width.

The top-left menu shows "Common Features / Input Methods / Keyboard Mode" horizontally centred at the top, with the back button and the more entry sharing a fixed position on the left. Categories use a darker pill base plate, and square icon options adapt to the actual count and width: when a single row fits they are not forced into a second row, otherwise they split evenly into two rows, and narrow screens scroll horizontally. Icon blocks use 24vp horizontal spacing. The native Swiper provides a 220ms animation, and the top selected block stays in sync frame by frame. A normal candidate commit does not show the manual recovery button; it appears only after a timeout or failure.

Common Features includes settings, clipboard, voice polishing mode, font size, key sound, customise toolbar, common phrases, emoji, photo input, traditional input, swipe input, and English association. The automatic-reading implementation is retained: a build that enables that capability reads the system's current text when the input method connects to an ordinary input box, listens for copy changes and collects them automatically, and opening the panel also refreshes, with no need to tap the system paste button first. It is wired through the READ_PASTEBOARD permission and main app runtime authorization; when not yet authorized, tapping "Clipboard Authorization" leads back to the input box the first time. At most 30 local records are saved, supporting tap-to-paste, copy, pin, single-item delete, and clear, with deduplication and pinned items kept; password and unverified fields are not collected, leaving the input box unregisters the listener and discards stale reads, and records are not uploaded. The system interface only provides the current clipboard, so history the app did not record cannot be recovered. A single history entry holds at most 16384 characters; "Paste current content" reads the complete text directly and is not limited by history length. Automatic reading is retained as an optional build capability: the default package does not declare READ_PASTEBOARD, does not request that permission, and does not listen for copy events; the existing local record feature is still available through the system paste button. After obtaining a signed Profile that includes READ_PASTEBOARD, building with OPENLESS_HARMONY_CLIPBOARD_ACCESS=1 enables both the permission declaration and automatic reading. That option does not replace system authorization and does not modify the signing Profile; installation without approval returns 9568289. The save queue is serialized, waiting for existing saves before switching input boxes, avoiding a clear being restored by a late write; polishing mode uses the shared backend; font, key sound, and swipe switches are saved locally, and key sound uses local short effects and follows media volume. Common phrases provide preset phrases. The settings entry opens the main app directly. Under Input Methods, "Dictionary & Cloud Candidates" retains Google cloud candidates, public dictionary updates, and switching to the system input method. When not composing, the four fixed shortcut slots in the middle can be long-pressed to edit and save.

Input Methods shows the 26-key, 9-key, and handwriting input methods; currently the 26-key is wired up. The 9-key, handwriting, photo, traditional, and English association entries display only an explicit disabled "To be wired up" entry, and these new engines are not implemented in this round. Keyboard Mode provides thumb (the existing split layout), standard, floating, and right one-handed layouts; one-handed content width is at most 420vp and no more than 72% of the screen width, and all panel content is right-aligned with the layout.

### Offline Dictionary and Cloud Candidate Upgrade

Dictionary warm-up runs in parallel when the extension is created and shares the same Promise as input box initialization, without creating a learning session or a cloud query. Initial resource copying uses asynchronous chunked writes and atomic rename of a temporary file, avoiding UI blocking from synchronous writes of large files; the full typing self-check does not run on the input box readiness path, and main app diagnostics can still call `testRime`. First installation/dictionary upgrade still requires a Rime deployment compile, and later runs reuse the cache. `scripts/harmony-rime-startup.test.mjs` covers parallel initialization, short writes, resource buffer boundaries, and failure retry.

Both ends share a pinned-revision Rime Fog Chinese dictionary and spelling rules, and an existing local `rime-user/pinyin_simp.userdb` is kept. The Rime Fog Lua tools and grammar model are not bundled. New resource directories are versioned separately, preventing an already installed app from skipping a dictionary update.

"Cloud candidates" in the keyboard tools is off by default; the description states clearly that the current pinyin will be sent to Google, and a query happens only after the user enables it. It applies only to non-password boxes with known attributes, and local candidates are kept on failure; text surrounding the input box is not handed to the cloud service. Candidate replies and selections are each validated against the input version, and after a cloud result is inserted, local candidates are still selected by native index. See `mobile-ime/README.md` for more details.

Startup lifecycle regression covers the system not passing a Want, empty parameters, and the authorization entry; EntryAbility handles missing startup parameters as null. The fixed build has been installed on a real device, and the user confirmed the main app reopens. Main app voice host regression covers start/stop, volume, duplicate start, recording and volume test mutual exclusion, cancellation during processing, cleanup on leaving the page, permission denial, and late callbacks.

When saving multimodal credentials, omni.* fields without a specified provider are bound to the current provider; the Asset Store's old global alias is bound to the current provider on restore, and records with an explicit provider take precedence, avoiding restore order overwriting new values. Saving and clearing clean up the old alias, preventing old values from reviving after a restart. Host tests cover Alibaba Cloud credential save/restore, the no-credential state, clearing, provider switching, and starting recording/receiving PCM/cancelling with the real shared multimodal engine (no network request is sent).
