# 按输入应用选择风格包

macOS 和 Windows 的入口为「风格 → 自动风格」，与润色模式、风格市场并列。页面采用固定看板。左侧每行以分类名称按钮和分类风格选择组成；点击分类名称打开独立应用选择弹窗，右上角显示当前分类，支持搜索、勾选和卡片列表竖向滚动。已勾选的应用排在前面，两组各自按应用名称排序。右侧管理实际输入过的应用及其指定风格，支持按名称搜索；每张紧凑卡片左侧显示应用名称和分类，右侧同一行选择风格。右侧列表和应用选择弹窗均连续滚动，无分页按钮，滚动条隐藏；搜索框、标题和底部操作区保持固定。右上角提供「清理应用记录」。应用选择与确认弹窗共享单色底板，固定弹窗的底部按钮直接放在右侧；滚动正文限定在标题和操作区之间，保留必要的上下遮挡。

## 分类目录 API

官方目录的唯一数据源位于 `openless-marketplace/catalogs/app-catalog.json`。市场服务从外部文件读取，提供以下公共只读接口。更新目录文件即可更新查询结果。

| 接口 | 用途 |
| --- | --- |
| `GET /v1/app-catalog` | 完整目录，用于客户端识别缓存 |
| `GET /v1/app-catalog/categories` | 分类及场景术语提示 |
| `GET /v1/app-catalog/clients?category=coding` | 按输入用途查询客户端 |
| `GET /v1/app-catalog/clients?role=agent_harness` | 按软件角色查询 Harness |
| `GET /v1/app-catalog/clients?provider=deepseek&platform=macos` | 按关联模型提供方和平台筛选 |
| `GET /v1/app-catalog/clients/:id` | 单个客户端及来源 |
| `GET /v1/app-catalog/model-families?provider=deepseek` | 模型族与 API 模型标识 |
| `GET /v1/app-catalog/model-families/:id` | 单个模型族 |

分类 ID、应用身份、别名、软件角色、模型关联、场景提示和来源均来自目录。客户端只保留数据协议、通用匹配与用户规则。`category` 表达输入用途，`role` 表达软件角色。Harness 可以属于编程；模型族通过 `modelFamilyIds` 与客户端关联，当前选中的模型仍由实际会话决定。[研究表与来源](../research/agent-app-model-catalog.md)

Core 的 [AppCatalogStore](../../openless-all/app/crates/openless-core/src/app_catalog.rs) 使用 Marketplace 的基地址获取完整目录。APP 启动、进入自动风格页面、窗口返回前台或恢复显示时自动刷新目录；页面内重叠的刷新事件合并为一次请求。桌面宿主焦点通过当前 Tauri 窗口的 focus 事件监听，覆盖隐藏主窗口后的重新打开。成功后通过现有原子写入工具保存 `input-app-catalog-cache.json`。请求或解析失败时保留最近一次可用目录。窗口恢复显示或焦点时立即读取本机应用记录，不等待目录请求；目录更新成功后再刷新分类。首次启动且没有可用目录时，应用指定规则和手选风格继续工作。

服务端须先部署目录接口及外部文件，再分发改用 API 的客户端。目录服务代码与接口验证通过代表可部署；生产地址实际返回有效目录后，才具备新客户端首次获取分类的条件。

## 识别与分类归属

macOS 用目录中的 Bundle ID 匹配。安装式 Web App 同时匹配目录中的 bundle 前缀和完整应用名称。普通浏览器标签页按浏览器本身处理。Windows 分类匹配宿主捕获的可执行文件名；单应用规则继续用可执行文件路径的本机指纹，避免保存路径。同名安装器、CLI 命令和 IDE 扩展由目录保留其实际软件形态。

`canonicalClientId` 指向同一身份的规范客户端，例如更名前后的产品。界面合并这些条目的身份，并保留研究查询入口。应用多选提供有桌面识别依据的目录客户端，以及成功听写中记录的目标应用。

每个应用最多归属一个分类。未调整时采用官方目录归属，用户调整后使用本机规则。取消勾选保存明确的未分类状态，后续目录刷新仍保留这个选择。其他分类中的应用显示 X。点击后展示当前分类及分类风格，经确认将归属移到目标分类。移动分类后，应用指定风格继续优先。

官方客户端的归属使用 `catalog:<clientId>` 保存，因此首次听写前即可调整。目录尚未识别的历史应用使用宿主提供的应用 ID，用户可将其加入任意已提供的分类。API 的类别 ID 采用字符串，新增类别和条目通过数据更新提供。

## 风格选择与会话时序

| 情况 | 结果 |
| --- | --- |
| 应用指定风格可用 | 使用该风格 |
| 应用没有可用的指定风格 | 使用有效归属分类的可用风格 |
| 分类未配置、应用未分类或无法识别 | 使用手选风格及现有默认回退 |
| 多个应用或分类选择同一个风格包 | 可以共用，各目标独立保存一个选择 |
| 风格包停用、删除或暂时缺失 | 保存规则并显示不可用，沿优先级寻找可用风格 |
| 用户移动应用归属 | 下一次会话采用新分类，具体应用风格继续优先 |
| 录音中切换窗口、更新目录或修改规则 | 本次目标、风格与场景提示使用开始时的快照 |

宿主在听写开始时成对捕获落字目标和应用上下文。Core 在异步光标读取和凭据访问之前，从本地目录快照解析应用身份、有效归属、候选风格及场景提示，然后冻结本次选择。实际模型请求取用本次风格的模式、提示词和建议模型。分类过程读取已获取的目录快照，听写开始无需等待目录网络请求。

分类及客户端的 `promptGuidance` 仅辅助理解术语和对象。用户风格定义输出任务，应用上下文和历史只提供理解素材。固定输出可以在多次输入中重复。内置原文模式在取消翻译后仍直接输出原文，即使开始时已捕获应用提示；自定义原文提示仍调用模型。原文、翻译、短文本跳过润色、自定义润色策略、选区润色和重新润色继续沿用各自的调用规则。

最终写入由宿主复核原目标。Windows 使用同一次捕获的窗口、进程和线程。macOS 恢复原应用并在可获得窗口编号时检查原窗口。同窗口标签页等细粒度目标仍取决于宿主能力。

## 冻结应用场景前缀

普通前台落字听写由 `capture_dictation_context_with_host` 从 `CapturedTextTarget.host_context` 同步获取 `input_app()` 和可用的 `input_location()`，在异步光标捕获及渠道凭据读取前，用同一次本地目录/用户归属快照确定分类、用途参考与候选风格。`options.front_app` 只是调用方上下文，不能替代实际写入目标的身份；没有稳定目标身份时名称/标识写“未知”，不能拿后来前台的 app 补齐。不会读取应用历史来构建本次前缀，也不上传历史到公共目录 API。

`DictationPolishContext.input_scene_prefix` 单独保存已渲染的短前缀，与 canonical `style_system_prompt` 分开。格式为：

```text
当前应用：{目标应用名称，否则未知}
应用标识：{宿主现有目标 ID，否则未知}
应用分类：{用户覆盖后的有效分类名称，否则未知}
应用主要用途：{官方客户端 promptGuidance 用途参考，否则未知}
当前输入位置：{可信目标位置，否则应用内输入，无法正确确定}
本次输入场景：{已有分类用途参考及谨慎的组织建议}
请结合上述信息理解用户的输入场景，再按照后续提供的用户风格要求处理本次语音内容。保持用户的原意，不自行增加需求或推断无法确定的信息。
```

目录没有独立的主要用途字段，现有客户端 `promptGuidance` 是唯一复用的用途参考；为空就如实未知，不根据应用名、分类或 role 自行生成用途。分类提示只在场景行提供参考，不改变风格指定的输出任务，不替用户添加开发任务、方案或回答问题。用户改分类只影响下一段；已开始的录音与已提交段不会因目录刷新、改规则、切窗口而变化。

`HostContextAdapter::input_location()` 是 object-safe 默认方法，默认返回 `None`。实现只能返回同一冻结目标中已验证的控件语义标签/角色，禁止从输入正文、窗口标题推断“搜索框”“聊天框”等位置。以下三种情况都原样显示“应用内输入，无法正确确定”：光标上下文开关关闭（不调用位置方法）；宿主无读取权限或无法确认位置；当前宿主尚未实现可信标签快照。当前桌面 AX/UIA 目标保留身份和范围，没有已经验证可消费的标签 getter，因此默认未知；这不表示平台本身无法提供标签。现有光标正文的隐私开关和权限路径保持原样。

传统润色在 `run_cloud_polish` 请求构建时调用 `with_input_scene_prefix`，统一系统提示词与 Omni 走 `effective_polish_prompts` / `build_omni_prompt`。序列化顺序为 **场景前缀 → 所选风格（内置修正在包内）→ 非内置修正尾缀 → 本次完整输入**；翻译协议及其他既有约束沿用原实现。旧的“输入场景参考”追加块已移除，不重复注入。Raw 的模式和 canonical 提示词判断完全不含场景，取消翻译仍可零模型直通。显式自选包优先于自动规则；调用方显式提供 `front_app` 时保持原有手选回退（除非同时指定 `style_pack_id`），真实目标元数据仍独立用于场景前缀；其余调用仍为具体应用 > 分类 > 手选。内部速记、云笔记、问答和选区不采用前台场景前缀，也不因此改变它们原有的选包规则。

## 本机数据与刷新

`app-style-routing.json` 保存分类风格、应用指定风格、归属覆盖，以及输入目标的标识、名称和使用状态。应用特征只包含识别和配置所需元数据。成功插入或发送粘贴的听写新增目标应用。页面订阅现有历史变更事件，输入完成后更新列表；返回前台时重新读取。

清理应用记录移除未配置目标，仍有本机规则的历史应用保留必要信息。官方客户端归属独立保存。图标由系统或现有本机图标缓存提供。用户归属、应用历史和目录缓存均为本机数据，沿用现有规则排除于云同步和迁移包。目录下载只请求公共表单，识别过程无需把用户的应用历史或输入文字发送给目录服务。

[跨层接口契约](../../openless-all/app/contract/backend-2.0.json)记录快照、刷新、归属修改和风格修改命令。

## 既有故障的证据边界

备忘录故障的历史元数据显示绑定的测试包已被选中，日志同时记录实际调用润色、未跳过短文本、无翻译和无插入错误。旧提示词却同时存在按应用调整语气、保持原意和避免重复历史输出的要求，与自定义固定输出任务冲突。代码已修正这些要求的优先级。

当时未保留实际发往模型的完整请求，也未完成同条件的真实模型对照，因此只能确认这些冲突存在。将其直接表述为已证实的唯一根因超出了证据。现有完整听写测试检查生产请求序列化、返回结果传递和原目标写入，并比较应用绑定与手选同一风格的请求消息。该测试使用本地模型服务夹具，真实模型对指令的执行效果仍需单独实测。

新建风格误开旧包来自列表刷新与编辑对象选择的异步竞争。创建流程已直接采用返回的新包并同步更新选择引用，相关浏览器测试覆盖重叠变更事件。
