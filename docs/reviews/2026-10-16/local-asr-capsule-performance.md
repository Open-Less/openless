# 本地识别资源占用与多屏胶囊

## 范围

基线 beta `96278f40`。处理更新后多屏同时显示胶囊、macOS 本地识别启动/停止等待和资源突增；不更改用户模型开关、凭据、录音、权限或已安装 App，不改已公开版本及标签。当前机器已有 SenseVoice 与 TextStream 权重，Gemma 不具备本次真实模型测试条件。

## 原因与修正

### 停止响应

普通听写在麦克风启动后仍 await `buffered.attach()`，本地模型加载/校验未完成时，Core 公开状态仍为 Starting。`stop_dictation_session_with_options` 会等待该状态结束，导致用户已点停止但麦克风不能及时释放、思考状态也迟迟不出现。SenseVoice 合成音频测试中冷加载约 8–10 秒，能解释这类等待；它不是关闭按钮没有绑定。

只对实验本地 ASR 使用宿主 TaskSpawner 后台 attach。麦克风已就绪即可进入 Recording；停止先释放 capture 并进入正常识别收尾，结果仍等待真实模型输出，不伪造完成。模型启动失败通过 RecordingFault 反馈，finalizing 后由 finish 返回原始错误；取消前尚未调度的加载不执行，加载中取消后的迟到 session 不回放音频并清理。云端管线和先录音后识别的稳定模式不改变。

### CPU、内存与加载

- TextStream 每次启动都会重新读取并 SHA-256 校验约 1.9 GB 固定权重。新增仅存在当前进程的校验缓存，文件目录、设备、inode、大小及 mtime/ctime（纳秒）未变才复用；首次、替换、修改或新进程仍全量校验，校验前后发生变化不缓存。没有写入可跨进程复用的信任标记。
- MLX 默认内存指导上限为推荐工作集的 1.5 倍，空闲缓存默认也可增长到该上限。现在显式设置工作集指导值为物理内存的三分之一、推荐工作集与 4 GiB 的最小值；空闲缓存最多 128 MiB，并在加载/识别片段/最终化后释放不再使用的缓存。它不是 OS 级硬 RSS 限额，活动模型权重和 KV 状态不会被强删。
- 原 CPU 总预算可能达到 5–7 个逻辑核，线程参数最多 2 不等于全部 native 辅助线程总用量最多 2。现在协作式平均预算另加 2 个逻辑核上限，保留 utility QoS 和可取消让步；单次不可分割 native 调用仍可能短时突发。
- SenseVoice 先前按采样到的空闲 CPU 调整线程，忙闲变化可能重建整个 ONNX 模型；创建新模型时旧模型还在 slot 内，造成双份驻留峰值。SenseVoice 固定单 CPU 推理线程，已加载实例不因预算变化重建；必须替换的实例在构造新模型前释放。单线程优先降低争用，不承诺更快的批量推理。
- 补充无文本的模型加载、包校验缓存命中、ready 和解码阶段计时。
- 受管 TextStream worker 自动升级同时识别已知旧脚本/环境指纹，保留 Python 环境和权重；未知或修改过的脚本不覆盖。lease/status 能识别可升级版本，防止旧 worker 在进入 refresh 前被拦截。

### 多屏

后续用户明确要求两种模式自行选择：本轮 Beta 在设置增加 `capsuleDisplayMode`，默认 `cursorScreen`，显式选择 `allScreens` 时才镜像。macOS/Windows 共享策略，macOS 镜像转换为非激活面板并使用目标屏幕逻辑坐标；Windows 保留独立原文 rail。设置同步、恢复和主线程缓存均接线，模式切换使镜像缓存失效。默认值、序列化重载、无效值拒绝、原生模式缓存及两个 OS 的双浏览器控件测试通过。

复查发现频繁销毁/重建 WKWebView 会累积原生资源，因此改为有限槽位复用：不用的窗口隐藏并投递 Idle 停止动画，实时 capsule 状态只发往可见镜像；不为每块屏幕创建额外识别会话。以下是最初单屏修复的历史说明，新 Beta 已不再强制用户只能单屏。

Windows #1183 曾主动增加“主屏固定胶囊 + 其他屏幕镜像”，因此两个屏幕同时显示是该版本的明确行为，不是识别引擎创建两份 UI。现在只显示鼠标所在屏幕上的一个 capsule / transcript rail，兼容路径隐藏已有镜像；鼠标不可读时回退主屏。混合 DPI、负坐标屏幕和卡片模式使用同一定位依据。

macOS 镜像创建原本就被 cfg 排除，继续保留现有鼠标屏幕定位；不把 Windows 镜像根因冒称为 macOS 双胶囊已复现。本机没有完成 Windows 真双屏 UI 操作，定位与重复窗口策略由纯几何回归验证，Windows 编译需云端门禁。

## 合成音频对比（本机开发验证，不是所有设备性能保证）

TextStream 使用同一 30.46 秒英语合成音频、相同已有权重和平均 2 核预算，直接启动生产 worker；100ms 采样 worker RSS/CPU，输入由独立发送线程供给，不阻断采样。未读取用户音频。

| 指标 | 修正前 | 修正后 |
| --- | --- | --- |
| worker 峰值 RSS | 1674.14 MiB | 1340.75 MiB |
| 首个草稿（含启动） | 2.18s | 1.65s |
| 最终结果（含启动） | 9.21s | 8.76s |
| 合成音频转写 | 完整 | 与修正前相同 |

RSS 降约 20%，采样 CPU 峰值约 88.5% / 90.3%，这次样本不支持“CPU 峰值已下降”的结论；平均预算与线程约束由计时回归验证。

SenseVoice 单线程实测：6.092 秒合成音频识别正确，冷加载 9.72s，随后 warm prepare 112ms，解码约 1.03s。此前两线程一次约 544ms；单线程降低争用会增加这段解码时间，不能包装成普遍提速。

TextStream 包校验在 debug 未优化 SHA 实测 cold 53.07s、warm 约 50µs，仅说明避免重复全文件读校验有效；不将 debug 耗时当作用户 Release 包的真实耗时。

## 本机与磁盘边界

磁盘此前开发构建缓存已清理，当前可用空间约 79 GiB；本轮只用一个共享 validation target、2 个构建任务、关闭 incremental/debug info，没有重建多个工作区的 target。未删除未经确认的系统快照。本轮验证结束后清理不再需要的临时构建产物，保留小型日志与对比结果用于复核。
